# FIX-260908 — 수신전용 스레드에 아웃박스가 생겨 "thread is receive-only"로 영구 실패

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-09-08 |
| 발견 경위 | FIX-260908(릴레이 페이지 봉투) 배포 검증 로그에서 `outbox 1791 failed permanently after 1: thread is receive-only` — 채널 5(amoebaorder)의 SMS 스레드 14개 전부, 스테이징 전체 473건(8/12부터, [[messenger-relay-staging]]의 "63건 백로그"가 계속 자라던 것) |
| 근본 원인 | `MessengerOutboxService.flushThread`가 대화의 모든 비고객 메시지(동의 안내·CSAT 질문·인계 안내·AI 답변)를 **스레드의 `reply_enabled`를 보지 않고** 큐에 넣고, 발송 단계 `deliver()`에서야 수신전용 가드가 영구 실패로 떨어뜨림. 즉 가드가 "만들지 않기"가 아니라 "만든 뒤 죽이기" 위치에 있었음 |
| 증상 | 수신전용 SMS 스레드마다 최소 1건(동의 안내)의 `failed` 아웃박스 행이 쌓이고 로그에 WARN 반복. 실제 발송 시도는 없었으므로 릴레이 측 부작용은 없음 |
| 수정 | `messenger-outbox.service.ts` `flushThread`: `reply_enabled != 1`이면 스캔한 메시지를 큐에 넣지 않고 커서만 전진. `deliver()`의 가드는 스레드가 나중에 수신전용으로 바뀐 경우를 위해 유지(심층 방어) |
| 검증 | `messenger-outbox.service.spec.ts` +1(수신전용 스레드: 큐 0건·커서 전진), 16 통과, `turbo typecheck` 통과; 스테이징 배포 후 채널 5 receive-only 실패 건수 증가 0 확인(§검증 기록) |

## 예방 패턴

**"할 수 없는 일"은 큐에 넣는 쪽에서 거른다.** 실행 단계의 가드는 마지막 안전망이지 필터가
아니다 — 실행 단계에서만 거르면 큐·로그·통계에 "실패"가 쌓이고, 운영자는 실패가 아닌 것을 실패로
읽는다(릴레이가 죽었나, 계정이 풀렸나). 큐 생성 조건과 실행 가드는 같은 술어(`reply_enabled`)를
공유해야 하며, 생성 쪽이 먼저 걸러야 한다.

**따라오는 질문(미결)**: 수신전용 스레드에는 동의 안내·CSAT 질문 자체를 만들 이유가 없다 —
고객이 절대 못 보는 문장이 콘솔 대화창에 "보낸 것처럼" 남는다. 세션 시작 시 스레드가
수신전용이면 안내류 시스템 메시지를 생략할지는 동의 정책(POL) 판단이 필요해 이번 수정에서 제외.

기존 473건의 `failed` 행은 종결 상태라 그대로 둔다(재시도 없음, 통계 영향은 아웃박스 실패 수치뿐).
