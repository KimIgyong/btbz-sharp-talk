| 항목 | 내용 |
|---|---|
| 작성일 | 2026-09-09 |
| 요청 | "세션 530 — 기본채널값(끔)인데 동의 안내 자동응답이 실제로 전송되었음. 이 자동응답도 대화방 설정에 따라 적용되어야 함" |

## 0. 한 줄 요약

메신저 채널의 **개인정보 동의 안내**("안녕하세요. 시작 전에 안내드립니다 — …")는 채널이
`consent_mode='notice'`이면 **자동응답 설정과 무관하게** 새 대화의 첫 인입에 무조건 만들어져
고객에게 발송된다. 자동응답이 꺼진 채널·대화방에서는 AI가 아무것도 처리하지 않으므로 이 안내는
근거 없는 자동 발신이며, 운영자가 "끔"으로 둔 방에 시스템이 먼저 말을 거는 결과가 된다.

## 1. AS-IS

### 1.1 재현 사실 (스테이징, 2026-09-08 16:30 UTC)

| 항목 | 값 |
|---|---|
| 대화 | 530 (콘솔 `/live-chat`의 "세션 530"은 대화 id) · 세션 6338 · 카카오톡 단체방(외부 스레드 4989) |
| 채널 5 (amoebaorder, btbz 릴레이) | `reply_mode=off`, `auto_reply=0`, `consent_mode=notice` |
| 세션 | `auto_reply_mode=off`(운영자가 이후 명시 지정; 생성 시점엔 `inherit` → 유효값 끔) |
| 발송 | 메시지 16372(system, KO 안내) → 아웃박스 1750 `unconfirmed`, 릴레이 커맨드 379 — **실제 방으로 나감** |
| 규모 | 채널 5 첫 동기화(FIX-260908 배포 직후 콜드스타트)에서 답장 가능 방 **37개 전부**에 안내 발송(`unconfirmed` 37), 수신전용 SMS 14개는 큐 실패 |

콘솔에는 이 안내가 대화 맨 위에 회색 system 말풍선으로 표시된다(숨겨진 것이 아니라 눈에 잘 띄지 않을 뿐).

### 1.2 코드 경로

`messenger-ingest.service.ts`
- `resolveConversation()` — 새 대화 생성 직후 `channel.consentMode === 'notice'`이면 **무조건**
  system 메시지(`CONSENT_NOTICE[lang]`) 저장. 자동응답 유효값(`resolveReplyMode`)은 그 **뒤**에
  계산된다(`ingestOne()` 본문).
- `resolveSession()` — 채널 세션은 생성 시 `consent_state='granted'` + 현행 `consent_version` 기록
  (외부 메신저에는 동의 배너가 없으므로 플랫폼 약관을 근거로 즉시 부여, PLN-260810 D-4).
- `ingestOne()` 말미 `outbox.flushThread()` — 대화의 비고객 메시지(안내 포함)를 즉시 발송.

즉 안내는 "AI 처리 전 고지"라는 취지(REQ-260810 G3)로 설계됐지만, 구현은 "대화 생성 시 고지"라서
AI가 개입하지 않는 방에도 나간다.

### 1.3 동의 게이트와의 관계 (제약)

`effectiveConsentFor()`가 `granted`가 아니면 **AI 파이프라인뿐 아니라 상담원 답장(`agent.service`
sendAgentMessage)·시나리오·이메일 수집도 차단**된다(Privacy-Control-Gap D-1, fail-closed).
따라서 "안내를 보내기 전까지 동의를 `pending`으로 두는" 방식은 자동응답 꺼진 방에서 상담원까지
막아 버리므로 채택 불가. 동의 부여 시점(세션 생성)은 그대로 두고, **안내 발송 시점만** 옮겨야 한다.

### 1.4 자동응답 유효값 (PLN-260812)

`상담원 점유 > 세션 설정(on/off/inherit) > 채널 기본값(reply_mode auto/approve/off)`.
새 대화의 첫 인입 시점엔 세션이 방금 생성되므로 세션 설정은 항상 `inherit` → **채널 기본값이
곧 "대화방 설정"**이다. 이후 운영자가 세션을 `on`으로 바꾸면 다음 인입부터 AI가 답한다.

## 2. TO-BE

**동의 안내는 "이 대화에서 AI가 처음 처리하기 직전"에 한 번 보낸다.**

| 상황 | AS-IS | TO-BE |
|---|---|---|
| 채널 끔(또는 세션 끔) 방에 첫 인입 | 안내 발송 | **안내 없음**, 메시지 저장·이관만 |
| 채널 켬 방에 첫 인입 | 안내 → AI 답변 | 동일(안내 → AI 답변) |
| 끔이던 방을 운영자가 `켬`으로 전환 후 다음 인입 | (이미 발송됨) | **그때 안내 → AI 답변** |
| 승인 모드(approve) | 안내 → 초안 | 동일(AI가 처리하므로 안내 유지) |
| 상담원 점유 중 | 안내 발송(새 대화면) | 안내 없음 |
| 수신전용 SMS 스레드 | 안내 생성 → 큐 실패(FIX-260908 후 큐 미생성) | 안내 생성 자체를 안 함 |
| `consent_mode='auto'` 채널 | 안내 없음 | 동일 |
| 같은 방(스레드)에서 대화 종료 후 새 대화 | 새 대화마다 안내 재발송 | **스레드당 1회**(안내 버전이 바뀌면 다시) |

동의 상태(`consent_state=granted`, 세션 생성 시) — **변경 없음.** 근거는 PLN-260810 D-4(플랫폼 약관)
그대로이며, 안내는 AI 처리에 대한 고지로서 처리 직전에 붙는다. → 정책 판단 필요 시 §5 참조.

## 4. 사용자 흐름

1. 운영자가 채널을 기본 끔으로 연결(비공식 카카오 방 운용 규약 R-1). 방 37개가 유입돼도 **아무 것도 발신되지 않는다.**
2. 운영자가 특정 방을 골라 자동응답 `켬`. 그 방의 다음 고객 메시지에 안내 1건 + AI 답변이 나간다.
3. 그 방이 종료 후 다시 열려도 안내는 반복되지 않는다(안내 문구 버전이 바뀌지 않는 한).

## 5. 제약·가정

- **정책 가정(확인 요청)**: 자동응답 꺼진 방은 상담원이 수동 응대하며 대화 기록은 저장된다. 이 저장에
  대한 고지는 현재도 세션 생성 시 `granted`(약관 근거)로 처리되고 있으며 이번 변경은 그 부분을 건드리지
  않는다. "기록 저장 고지도 항상 보내야 한다"가 정책이면 이 요구사항과 상충하므로 결정 필요.
- 이미 발송된 37건은 회수 불가. 스테이징 데이터라 조치 없음.
- 스키마 변경 1컬럼 → 스테이징 `DB_SYNCHRONIZE=false`이므로 SQL 선적용 필요.
