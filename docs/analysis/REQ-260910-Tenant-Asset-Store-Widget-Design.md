## 1. AS-IS

### 1.1 테넌트별 파일 저장 — "폴더"는 있으나 규약이 없다
단일 볼륨 `UPLOAD_DIR`(스테이징 `/data/uploads`, 볼륨 `staging_ivy_uploads_staging`) 아래에 기능별로 제각각의 경로:

| 영역 | 경로 규칙 | 등록부(DB) | 서빙 |
|---|---|---|---|
| 채팅 첨부 | `{tenantId}/{YYYY-MM}/{uuid}.{ext}` (+`_t.webp`) | `message_attachments` | 서명 URL 15분/외부 7일 |
| 위젯 로고 | `{tenantId}/branding/{id}.{ext}` | `tenants.widget_theme.logo` (JSON) | 공개 `GET /tenants/widget-branding/logo?v=`, `v`=id 일치 시 immutable |
| AI 인제스트 원본 | `kb-ingest/{tenantId}/…` | `kb_ingest_*` | 내부 |
| 보드 첨부 | `board/{tenantId}/{uuid}{ext}` | `board_attachments` | 서명 URL |

- 테넌트 루트가 앞에 오는 경우(첨부·로고)와 기능이 앞에 오는 경우(kb-ingest·board)가 섞여 있어 **"테넌트 폴더 하나"로
  백업·용량 산정·이관·삭제(DSAR/테넌트 해지)를 할 수 없다.**
- API 이미지는 배포마다 재빌드 — 볼륨 밖의 파일은 다음 배포에 사라진다(compose 주석). **production compose(`docker/production/docker-compose.production.yml`)에는 API 컨테이너의 uploads 볼륨이 없다**(§4 SI-1) — 그대로 배포하면 로고·첨부가 재배포마다 사라진다.
- 파일 등록부가 기능별 테이블/JSON에 분산 — 테넌트 단위 용량·목록·정리 API 없음.

### 1.2 위젯 디자인 커스터마이즈 — 현재 가능한 것
`tenants.widget_theme`(JSON) → `normalizeWidgetTheme` → `session/ensure` 응답 → 위젯이 `:root` CSS 변수로 적용 +
shop별 localStorage 캐시(첫 페인트) → 로더 `embed.js`가 iframe 프레임 크기·위치 관리.

| 항목 | 현재 | 저장 |
|---|---|---|
| 브랜드색 | 1색 → 9단 램프 + 전경색(대비 4.5:1) | `brand` |
| 헤더 | white / brand | `headerStyle` |
| 로고 | png/jpg/webp ≤1MB, 1000×400, sharp 재인코딩, **svg 금지** | `logo{id,ext,mime,w,h}` + 파일 |
| 런처 | 위치 left/right · 크기 sm/md/lg(48/56/64) · 아이콘 chat/question/headset/logo | `launcher` |
| 문구 | 인사말·표시명 등 6언어 | `widget_copy` |
| 탭 | 노출 탭·위치 | `widget_tabs` |

### 1.3 요청한 항목의 현 상태
| 요청 | 현재 | 비고 |
|---|---|---|
| 폰트 | **고정** — `Pretendard`(jsDelivr CDN) + 시스템 폴백, `index.html`·Tailwind 하드코딩 | 테넌트별 폰트·크기 불가 |
| 아이콘 | 런처 4종 enum, 위젯 내부는 lucide 고정 | 테넌트 아이콘 파일 업로드 불가 |
| 화면 사이즈 | 로더 상수 `OPEN 444×680`, 패널 404px, 런처 3단 | 테넌트별 폭·높이 불가 |
| 디자인 컨셉 문서/시안 | 저장처 없음 | Figma 산출물은 `docs/`(개발자용)에만 |
| 설정 백업/이관 | 없음 — JSON 컬럼 5종은 DB에만 | 테넌트 단위 내보내기/가져오기 불가 |
| 커스텀 CSS/JS | 없음(의도) | 로고 svg 금지와 같은 이유 — iframe이 API와 동일 오리진 |

## 2. 요구 해석 (TO-BE)

| # | 요구 | 해석 |
|---|---|---|
| R1 | 테넌트별 폴더 | 볼륨 안 **테넌트 루트 규약** `tenants/{tenantId}/{area}/…` + 파일 **등록부 테이블**(`tenant_assets`)로 목록·용량·삭제·이관을 테넌트 단위로 가능하게. 기존 경로는 그대로 두고(이동 없음) 신규 영역만 규약을 따른다 |
| R2 | 위젯 디자인 파일 별도 저장 | `area=design`: 폰트(woff2)·아이콘(png/webp)·이미지·디자인 시안/가이드(pdf/png, 참고용). 콘솔 설정 > 위젯 "디자인 파일" 관리(업로드·목록·미리보기·삭제·다운로드) |
| R3 | 개별 커스텀(폰트·아이콘·크기) | `widget_theme`를 **구조화 토큰**으로 확장: 폰트(프리셋 또는 업로드 자산)·기본 글자 크기·모서리·패널 폭/높이(범위 제한)·런처/탭 아이콘(자산 참조). 위젯은 CSS 변수로, 로더는 프레임 크기로 소비. **자유 CSS/JS는 채택하지 않음**(§4 SI-5) |

| R5 | **배포와 분리된 테넌트별 위젯 디자인 관리**(2차) | 디자인을 **코드가 아닌 테넌트 데이터**(토큰 JSON + 자산 파일)로 두고, 테넌트 폴더에 **버전**(초안 → 게시 → 이전 버전 롤백)으로 보관한다. 게시는 콘솔에서 즉시 반영되며 API/위젯 **코드 배포와 무관**하다(볼륨·DB에 살고 이미지 재빌드에 영향받지 않음). 위젯 런타임(단일 빌드)은 부팅 시 테넌트의 **게시본**을 읽어 그린다. 디자인 패키지는 zip으로 내보내기/가져오기(다른 환경·테넌트로 이관) |

| R6 | **커스텀 위젯 만들기·사용함·복귀·보관**(3차) | 테넌트가 이름 붙인 **커스텀 위젯(디자인)**을 여러 개 만들어 **라이브러리에 보관**하고, 그중 하나를 **사용함**으로 적용한다. 사용함이 없으면 **기본 위젯**(현행 '위젯 테마' 카드의 브랜드색·헤더·로고·런처 = 기존 기능 그대로). 언제든 [기본 위젯으로 복귀] 또는 다른 커스텀으로 전환. 보관=목록 유지·복제·보관함(archive)·복원·삭제 |

### 2.1 "백엔드와 분리"의 의미 확정
| 해석 | 채택 | 이유 |
|---|---|---|
| (a) 디자인의 **수명주기**(작성·게시·롤백·보관)가 코드 배포와 분리 | **채택** | 요구의 본질. 데이터+파일 모델이면 배포 없이 게시·복구 가능 |
| (b) 위젯 디자인 **서빙**이 API 가용성과 분리(정적 파일) | **채택(선택 강화)** | 게시본을 `tenants/{id}/widget/live/design.json`으로도 써 두고 nginx가 정적으로 서빙 → 첫 페인트가 API 부팅·세션 왕복에 의존하지 않음 |
| (c) 테넌트별 **위젯 코드 빌드/배포 분리**(테넌트마다 다른 SPA) | **비채택** | 테넌트 수만큼 빌드·보안 패치·회귀 비용, 릴레이·SDK·앱모드 계약이 갈라짐. 단일 런타임 + 테넌트 디자인 데이터가 같은 결과를 배포 없이 낸다 |
| (d) 테넌트가 **CSS/JS를 직접 올려** 위젯을 바꿈 | **기본 비채택, 제한적 옵션** | 위젯 iframe에 대화 내용(PII)·세션 토큰이 있어 자유 CSS는 `url()`·속성 선택자로 유출 벡터. 토큰으로 부족한 테넌트를 위해 **허용목록 기반 정제 CSS**(url/@import/position 제외)를 별도 단계 옵션으로만 둔다(PLN §0 C′) |

### 2.2 적용 모델 비교 (3차 요구) — "선형 버전" vs "커스텀 위젯 라이브러리 + 사용함 스위치"

| 기준 | ① 테마 1개 + 선형 버전(2차 PLN D-12) | ② **커스텀 위젯 라이브러리 + 사용함 스위치**(3차) | ③ ①+② 혼합(디자인마다 버전 이력) |
|---|---|---|---|
| 기본 위젯 복귀 | "기본"이 버전 중 하나가 아님 → 별도 처리 필요 | **스위치 OFF = 기본 위젯**. 명시적·즉시 | ②와 동일 |
| 여러 시안 보관·비교 | 버전은 시간순 1줄 — 시즌별/캠페인별 시안 병행 불가 | 이름 있는 디자인 N개 병행(예: 기본·블랙프라이데이·봄) | ②와 동일 |
| 잘못 적용 시 복구 | 롤백(이전 버전) | 직전 적용 디자인 또는 기본으로 전환(이력 1줄 보관) | 디자인 내부 버전까지 롤백 |
| 편집 중 라이브 영향 | 초안/라이브 분리로 안전 | 적용 중 디자인을 직접 수정하면 즉시 반영 → **"복제 후 편집, 적용 전 미리보기"** 규칙 + 적용 중 디자인 편집 시 경고 | 초안 분리까지 가능 |
| 구현 규모 | 테이블 1 + 버전 로직 | 테이블 1 + 활성 포인터 1컬럼 | 테이블 2 |
| 운영자 이해도 | "버전"은 개발자 개념 | "만들기 → 보관 → 사용함" 이 요청 언어와 일치 | 개념 2중 |
| 판정 | ②로 대체 | **채택** | 과설계 — 필요 시 후속(디자인별 이력) |

결정: **② 채택**. 디자인 데이터 모델·자산·패키지 이관·정적 라이브 파일·미리보기(2차 결정)는 그대로 두고, "무엇이 라이브인가"만
**선형 버전 → 활성 디자인 포인터(없으면 기본 위젯)**로 바꾼다. 기본 위젯은 기존 '위젯 테마' 카드 설정이므로 **회귀 없음**: 모든 테넌트는
마이그레이션 직후 "커스텀 사용 안 함 = 기본 위젯" 상태에서 시작한다.

## 5. 제약·결정 근거
- 위젯은 **단일 빌드**를 모든 테넌트가 공유한다(iframe SPA). 테넌트별 "파일로 디자인을 교체"하는 모델(테마 번들·CSS)은
  빌드 모델·보안 경계와 충돌 → 커스텀은 **데이터(토큰+자산 참조)**로, 파일은 **자산(폰트·아이콘·이미지·시안)**으로.
- 자산 URL은 **버전이 URL에 있을 때만 immutable**(로고 규칙 승계).
- 아메바 철학(적정기술): 등록부 1테이블·라우트 1세트로 로고를 포함한 모든 파일 종류를 다루고, 로고 서비스는 후속에 등록부로
  수렴(이번엔 무이동).
